What is ODCS?

Open Data Contract Standard v3.1

  • Linux Foundation standard (Bitol project)
  • YAML-based contract definition
  • Covers: schema, quality, SLA, ownership, governance
  • Ecosystem: datacontract-cli, OpenMetadata
  • The competing spec was deprecated — ODCS won
apiVersion: v3.1.0
kind: DataContract
id: orders-contract
info:
  title: Orders Contract
  version: 1.0.0
  status: active
team:
  name: orders-team
  domain: commerce
schemas:
  - name: OrderEvent
    type: avro
    location: orders/OrderEvent:3
quality:
  accuracy:
    - name: positive-amount
      expression: totalAmount > 0
      threshold: 1.0
Speaker notes: ODCS is a YAML format that wraps around a schema with metadata about who owns it, what quality rules apply, what SLA is expected, and how sensitive the data is. Think of it as a "package.json for data" — the schema is the code, the contract is the manifest. We chose ODCS over building our own format because it's the industry standard, has tooling ecosystem, and Confluent can't match it (they have their own proprietary format).

How it Works: Projection Model

ODCS contracts are projected onto schema artifacts — not stored as a separate entity.

Speaker notes: The key insight: we don't create a new storage model for contracts. Instead, we project the contract's contents onto the schema artifact it governs. Quality rules become CEL contract rules. Metadata becomes labels. PII markers become version-level tags. This means enforcement happens through the existing rule engine — no new enforcement path. The ODCS YAML is also stored as its own artifact for versioning and export. Everything is namespaced by contractId so multiple contracts can coexist on the same schema.

Multi-Contract Support

Multiple teams can govern the same schema independently.

Contract A: Orders Team

contract.orders-contract.owner.team = orders-team
contract.orders-contract.status = STABLE
odcs:orders-contract:positive-amount (rule)

Contract B: Billing Team

contract.billing-contract.owner.team = billing-team
contract.billing-contract.status = DRAFT
odcs:billing-contract:valid-currency (rule)

Each contract's projection is isolated by its ID. Updating or deleting one contract never touches another's labels, rules, or tags.

Speaker notes: This was a critical design decision. Early versions used a flat label namespace (contract.owner.team) which meant only one contract per schema. We changed to namespaced labels (contract.{contractId}.owner.team) so multiple teams can independently define contracts for the same schema. The atomic merge operations in the storage layer ensure concurrent projections from different replicas don't corrupt each other.

Field-Level Tags

Automatic PII and sensitivity detection from schema content.

Avro

{"name": "ssn", "type": "string",
 "tags": ["PII", "SENSITIVE"]}

JSON Schema

{"email": {"type": "string",
 "x-tags": ["PII", "EMAIL"]}}

Protobuf

// @tag:PII,SENSITIVE
string ssn = 1;

Stored as version labels

field-tag.{contractId}:ssn|PII = EXTERNAL
field-tag.{contractId}:ssn|SENSITIVE = EXTERNAL
field-tag.{contractId}:email|EMAIL = EXTERNAL

No new storage tables. Tags reuse the existing label infrastructure — works across SQL, KafkaSQL, GitOps, KubernetesOps.

Speaker notes: Tag extractors automatically detect PII annotations in schema content when artifacts are registered. We support three formats: Avro's tags property, JSON Schema's x-tags extension (Confluent-compatible), and Protobuf's @tag: comment convention. Tags are stored as version-level labels using a pipe separator (|) to avoid ambiguity with dots in field paths. This was a deliberate design choice — using labels instead of a dedicated table means zero new storage infrastructure.

CEL Rule Execution

Real Common Expression Language via cel-standalone

Submit a contract with rules

quality:
  accuracy:
    - name: positive-amount
      expression: totalAmount > 0
      threshold: 1.0
    - name: valid-email
      expression: |
        email.contains('@') &&
        size(email) > 5
      threshold: 0.99

Threshold mapping:

  • 1.0 → ERROR (reject)
  • 0.95-0.99 → DLQ (dead letter queue)
  • <0.95 → NONE (log only)

Execute rules against data

POST /versions/1/contract/execute

{
  "mode": "WRITE",
  "record": {
    "totalAmount": -5,
    "email": "invalid"
  }
}

Response:
{
  "passed": false,
  "violations": [{
    "ruleName": "odcs:orders:positive-amount",
    "message": "Condition failed",
    "action": "ERROR"
  }],
  "executedRules": 2,
  "failedRules": 1
}
Speaker notes: We use the real CEL specification via Project Nessie's cel-standalone library — not a custom subset. This means full CEL support: parenthesized grouping, ternary expressions, string functions like contains/startsWith/matches, has(), size(), and more. The rule execution engine is in a separate Maven module (contracts-rules) with zero storage dependency, so it can be reused by the SerDes module in a future phase. AST compilation results are cached with a bounded LRU cache. The threshold-to-action mapping automatically determines whether rule failures should reject messages, route to DLQ, or just log.

Enterprise Ready

Multi-Replica Safe

  • mergeArtifactLabels — atomic prefix-scoped label updates
  • No read-modify-write on labels
  • DELETE prefix + INSERT in one transaction
  • Concurrent projections to different contracts don't conflict
  • Same contract projections are idempotent

Production Features

  • Always available (opt-in by usage)
  • Bounded CEL AST cache (1000 entries)
  • Label key length validation (max 512)
  • Projection rollback on failure
  • ReadOnly storage decorator support
  • Go SDK auto-generated
Speaker notes: For clustered deployments, we added mergeArtifactLabels and mergeVersionLabels to the storage layer. These do DELETE WHERE labelKey LIKE prefix% then INSERT — all in one database handle/transaction. This means two replicas projecting different contracts touch different label rows and can't conflict. The same contract projected twice simply overwrites with identical values. No JVM-local locking needed — atomicity is in the database. The CEL cache is bounded to prevent memory leaks from varied expressions. Projection failures roll back the contract artifact creation.

Storage Layer: How Atomic Label Merge Works

The Problem

Read-Modify-Write race:

Replica A: READ all labels
Replica B: READ all labels
Replica A: WRITE new labels (B's changes lost)
Replica B: WRITE new labels (A's changes lost)

The Solution

Prefix-scoped atomic merge:

-- In one database transaction:
DELETE FROM artifact_labels
  WHERE groupId=? AND artifactId=?
  AND labelKey LIKE 'contract.orders-contract.%';

INSERT INTO artifact_labels ...
  ('contract.orders-contract.status', 'STABLE'),
  ('contract.orders-contract.owner.team', 'orders');

-- Rebuild JSON column:
SELECT labelKey, labelValue FROM artifact_labels
  WHERE groupId=? AND artifactId=?;
UPDATE artifacts SET labels=? WHERE ...;

New Storage Methods

MethodPurpose
mergeArtifactLabelsAtomic prefix delete + insert for artifact labels
mergeVersionLabelsAtomic prefix delete + insert for version labels
selectArtifactLabelsRead labels for JSON column rebuild
deleteArtifactLabelsByPrefixDelete labels matching a prefix
deleteVersionLabelsByPrefixDelete version labels matching a prefix

Safety Guarantees

  • Different contracts → different prefixes → no conflict
  • Same contract → idempotent overwrite
  • ReadOnly decorator guards all write methods
  • Label keys >256 chars rejected (not truncated)
  • No JVM-local locks needed — atomicity in DB
Speaker notes: This is the key enterprise change. The original implementation used read-all-labels, modify, write-all-labels — which races across replicas. The fix: mergeArtifactLabels does DELETE WHERE labelKey LIKE prefix% then INSERT in a single database handle (transaction). Each contract's labels have a unique prefix, so concurrent projections to different contracts operate on different rows and can't conflict. After modifying the label rows, we rebuild the denormalized JSON column on the artifacts table by reading back all label rows. This keeps the JSON column in sync for GET responses. All new methods go through SqlStatements (no hardcoded SQL) and are covered by the ReadOnlyRegistryStorageDecorator. Label keys exceeding the 256-char VARCHAR limit are rejected with a clear error instead of silently truncated.

Known Limitations & Mitigations

LimitationImpactMitigationStatus
KafkaSQL eventual consistency Projected labels may be stale across replicas ODCS YAML is source of truth; re-submit to correct Architectural
Label key max 256 chars Long contractId + field paths may exceed limit Rejected with clear error (not truncated) Resolved
Promotion validation reads then writes Two concurrent promotions could race Uses mergeArtifactLabels (atomic prefix merge) Resolved
JSON column rebuild after merge Extra SELECT + UPDATE per projection Only happens during contract submit/update Acceptable
SerDes integration (opt-in) Rules execute on serialize/deserialize when enabled Config: apicurio.registry.serde.contract-rules.enabled Resolved
Speaker notes: Be transparent about these. The KafkaSQL limitation is architectural — projections modify SQL label rows directly, and in KafkaSQL mode these aren't journaled through Kafka. The ODCS YAML artifact IS journaled, so re-submitting corrects any inconsistency. The 256-char limit is the existing database column constraint — we now reject instead of truncate, which is the correct behavior. The most impactful limitation is the lack of SerDes integration — without it, rules only execute when explicitly called via REST. Phase 7 addresses this.
